PROJECT OVERVIEW
----------------
FreeFlow ASVPN is an all-in-one autoscript VPN installer built across 7 dev
sessions. It combines:
  - VLESS (WS / HttpUpgrade / XHTTP / gRPC / XTLS Reality)
  - VMESS (WS / gRPC)
  - Trojan (WS / gRPC / TCP)
  - SSH WebSocket tunnel
  - Cloudflare WARP routing
  - Per-user management, expiry, data limits
  - Telegram bot control
  - Auto-update from GitHub

Architecture: Nginx (reverse proxy) + Xray Core
SSL: acme.sh + Let's Encrypt ECC (ec-256)
OS Support: Ubuntu 18.04–26.04, Debian 9–13

--------------------------------------------------------------------------------
ROOT CAUSE #1 — Architecture Not Validated Before Deployment
--------------------------------------------------------------------------------
The Nginx + Xray architecture was designed in Session 1 and 3,525 lines of code
were written before any real VPS test. First real test was Session 5+.

Because Nginx proxies to Xray, failures can happen at 3 separate layers with no
cross-layer logging. Xray access.log stays empty whether the problem is Nginx,
Xray config, or the client. Every debug session started from scratch.

ROOT CAUSE STATEMENT:
  No integration test was run between architecture selection and first VPS
  deployment. The layered architecture was validated only on paper.

--------------------------------------------------------------------------------
ROOT CAUSE #2 — Cascading Silent Bugs (10 Bugs Stacked)
--------------------------------------------------------------------------------
By Session 5, 10 bugs were found. Several masked each other:

  Bug #9 (REPO_BRANCH in common.sh pointed to old branch)
    → v2.2 fixes never actually installed on VPS
    → All subsequent debugging was done on old broken code

  Bug #10 (WebSocket case: "Websocket" vs "websocket")
    → WS upgrade silently failed
    → Nginx returned 200 instead of 101
    → Xray never received connections — access.log empty
    → Looked identical to a firewall issue → wasted sessions on iptables

  Bug #2 (No firewall rules)
    → Ports appeared open but kernel blocked them
    → Red herring consuming Session 6

  Bug #6 (Nginx http2 incompatible directive)
    → Nginx ran with degraded config on older versions
    → Looked like SSL problem → triggered certbot → acme.sh migration

ROOT CAUSE STATEMENT:
  Bugs were introduced across independent scripts with no shared test harness.
  Compounded bugs produce identical symptoms regardless of which layer broke.

--------------------------------------------------------------------------------
ROOT CAUSE #3 — Wrong SSL Tool (certbot vs acme.sh)
--------------------------------------------------------------------------------
Initial SSL used certbot. All reference scripts (JinGGo, Decode, Darul Itqan,
Rerechan) use acme.sh. This was only noticed in Session 6 — 5 sessions late.

Certbot conflicts with Nginx on port 80 during renewal. acme.sh standalone mode
is the correct approach and was proven in the field by all references.

ROOT CAUSE STATEMENT:
  Reference scripts were analyzed for features but NOT for infrastructure
  decisions. Wrong SSL tool chosen because references weren't fully studied.

--------------------------------------------------------------------------------
ROOT CAUSE #4 — Client Misconfiguration Masked as Server Bug
--------------------------------------------------------------------------------
Session 7 confirmed server was 100% working:
  iptables: all VPN ports ACCEPT ✓
  nginx: running, config valid ✓
  DNS: resolves correctly ✓
  SSL: real Let's Encrypt ECC cert ✓
  WebSocket port 80 → HTTP 101 ✓
  WebSocket port 8443 → HTTP 101 ✓
  Xray access.log: EMPTY

Root cause of "dead end":
  V2rayNG had wrong server IP: 172.66.169.187 (Cloudflare CDN, not VPS)
  Wrong path: / (decoy page, not /vless-ws)

The server was NEVER broken in Session 7. The client was pointed at the wrong
server entirely. The session ended before re-testing with correct config.

ROOT CAUSE STATEMENT:
  Testing relied on manual client configuration. Own share-link generator was
  not used. One wrong IP routed all test traffic to a Cloudflare server.

CRITICAL BUG FOUND IN CODE — CONFIRMED BEFORE VPS ACCESS:

BUG #1: common.sh REPO_BRANCH = v2.1 (NOT v2.2)
  File: scripts/core/common.sh line 4
  Code: REPO_BRANCH="devin/1778775736-v2.1-ux-fix"  ← WRONG

  auto_update.sh sources common.sh and uses ${REPO_BRANCH} to download updates.
  Cron job runs every night at 4AM.

  What happens every night:
    1. auto_update reads VERSION from v2.1 branch → "2.1.0"
    2. Installed version is "2.2.0"
    3. 2.2.0 ≠ 2.1.0 → triggers update
    4. Downloads entire v2.1 scripts archive
    5. Overwrites ALL v2.2 scripts on VPS
    6. Restarts Xray and Nginx

  You test it, it works. Sleep. Wake up. Broken again. Every single morning.

  FIXED ON VPS: Changed to REPO_BRANCH="devin/1778798867-v2.2-critical-fixes"

BUG #2: SSH WS path never added to Nginx config
  setup.sh calls install_nginx_full BEFORE install_ssh_ws
  When Nginx config is generated, ssh_ws_installed flag doesn't exist yet
  /ssh location block never written → SSH WS clients hit decoy page (HTTP 200)

BUG #3: SSL failure not handled — Nginx crashes silently
  If acme.sh fails, cert files don't exist
  Nginx config references missing cert files → nginx -t fails → Nginx dead
  No error shown to user

BUG #4: gRPC on non-TLS ports silently fails
  gRPC requires HTTP/2. Non-TLS server block has no h2c enabled.
  gRPC to port 80/8080 always fails.
  FIXED ON VPS: Removed gRPC from non-TLS block

BUG #5: XHTTP missing proxy_buffering off
  XHTTP is a streaming protocol. Nginx buffers entire response by default.
  Connection times out → XHTTP never establishes.
  FIXED ON VPS: Added proxy_buffering off + proxy_request_buffering off

BUG A — CRITICAL: Ads Blocker Kills Server DNS Performance
--------------------------------------------------------------------------------
File:     scripts/tools/ads_blocker.sh
Confirmed: /etc/hosts has 82,628 lines — 82,620 are ad-blocking entries

The script appends the entire StevenBlack hosts list to /etc/hosts.
Every DNS lookup must scan 82,000+ lines linearly before querying DNS server.
On a VPN server with multiple users, this causes latency spikes on ALL connections.

Fix: Use dnsmasq (hash table lookup — O(1) not O(n)):
  apt-get install -y dnsmasq
  wget -qO- "https://raw.githubusercontent.com/StevenBlack/hosts/master/hosts" \
      | grep "^0.0.0.0" | grep -v "0.0.0.0 0.0.0.0" \
      | awk '{print "address=/"$2"/0.0.0.0"}' \
      > /etc/dnsmasq.d/freeflow-ads.conf
  systemctl restart dnsmasq

Immediate action on this VPS:
  sed -i '/# FreeFlow Ads Blocker/,/# FreeFlow Ads Blocker — End/d' /etc/hosts
  rm -f /etc/freeflow/modules/ads_blocker_installed

--------------------------------------------------------------------------------
BUG B — CRITICAL: Usage Stats Never Reset (Double-Counting)
--------------------------------------------------------------------------------
File:     scripts/user/usage_tracker.sh
Confirmed: xray api statsquery -reset is NOT a valid flag (confirmed via --help)

The reset line is silently ignored. Every 5-minute cron cycle adds the same
cumulative total on top of itself.

Result: A user doing 100MB/hour appears to use 1.2GB/hour in tracker.
Data limits trigger far too early.

Fix: Use delta tracking:
  last=$(cat "${USAGE_DIR}/${username}.xray_last" 2>/dev/null || echo "0")
  delta=$((total - last))
  [[ "${delta}" -lt 0 ]] && delta="${total}"  # handle xray restart
  echo "${total}" > "${USAGE_DIR}/${username}.xray_last"
  new_total=$((stored + delta))

--------------------------------------------------------------------------------
BUG C — HIGH: "Check User Login" Always Shows Zero Online
--------------------------------------------------------------------------------
File:     scripts/user/manage_user.sh → check_login_users()
Confirmed: loglevel is "warning" — accepted connections NOT written to access.log

The check_login_users() function greps access.log for user emails.
With loglevel: warning, access.log only has startup messages.

Result: Online Users feature in both shell menu and Telegram bot always
shows zero users, even when users are actively connected.

Fix: Change loglevel from "warning" to "none" in Xray config:
  "log": {
      "access": "/var/log/xray/access.log",
      "error": "/var/log/xray/error.log",
      "loglevel": "none"
  }
With loglevel "none", Xray still writes to access.log but suppresses console.
This is how all reference scripts (JinGGo etc.) work.

--------------------------------------------------------------------------------
BUG D — HIGH: Trial Account Expiry is Date-Only (Hour Precision Lost)
--------------------------------------------------------------------------------
File:     scripts/user/manage_user.sh → create_trial_account()
Confirmed: date -d '+60 minutes' +'%Y-%m-%d' = same day value, time stripped

Code:
  expiry=$(date -d "+${minutes} minutes" +"%Y-%m-%d")  ← strips time!

is_expired() compares date strings only.
A 1-hour trial created at 11PM stores expiry as next day's date.
Today > next_day = false → trial never expires until end of next day.

Result: 1-hour trial actually lasts up to 25 hours.

Fix:
  expiry=$(date -d "+${minutes} minutes" +"%Y-%m-%d %H:%M")
  # In is_expired():
  local now=$(date +"%Y-%m-%d %H:%M")
  [[ "${now}" > "${expiry_date}" ]]

================================================================================
  PART 5 — CLOUDFLARE SETUP & FINDINGS
================================================================================

WHY THIS MATTERS
----------------
ISP blocks direct connections to overseas VPS IPs in Malaysia/SEA region.
Cloudflare CDN acts as relay — traffic looks like normal HTTPS to Cloudflare.

REQUIRED CLOUDFLARE SETTINGS:
  SSL/TLS → Overview   Encryption mode   FLEXIBLE  (Full breaks WebSocket)
  Network              WebSockets         ON        (OFF by default)
  Network              gRPC               ON        (OFF by default)
  DNS → A record       Proxy status       PROXIED   (orange cloud ON)

WHY NETMOD WORKED BUT V2RAYNG/NEKOBOX DIDN'T:
  Netmod stored 172.66.169.187:80 (CF IP) directly
  V2rayNG/Nekobox used domain → resolved through CF → SSL=Full →
  CF tried HTTPS to VPS port 443 (Xray Reality, not web server) → failed

  SSL changed to Flexible → all 3 apps now work

FOR V2RAYNG WITH CLOUDFLARE CDN:
  Field    Value
  Address  172.66.169.187  (CF IP, NOT the domain or VPS IP)
  Port     80
  UUID     (your user UUID)
  Network  ws
  Path     /vless-ws
  Host     madvpn.us.kg   ← THIS IS CRITICAL (tells CF which origin to use)
  TLS      none

FEATURE REQUEST: CF-AWARE SETUP
  setup.sh should ask: "Will you use Cloudflare CDN proxy? [y/n]"
  If YES:
    - Store CF IP in /etc/freeflow/cf_ip
    - Generate ALL share links with CF IP as address + domain as Host
    - Print CF setup checklist at end of install
  This would have prevented all confusion across Sessions 4-7.
